# AccessProof — Provenance, Customer SSE and Route Verification Continuation

**Date:** October 22, 2026  
**Status:** LOCAL code changes only, no production deployment or real customer data.

## What was actually implemented

1. **Opt-in cryptographic source-byte verification**: `packages/rag_sdk/attestation.py` defines tenant/application/source/resource/chunk/version/byte-digest-bound Ed25519 source attestations. Signer custody is assigned to a separate trusted ingestion boundary; the customer-side RAG gets only a pinned public key.
2. **Pre-generation and post-generation enforcement**: `packages/rag_sdk/protection.py` verifies content attestations before model input, rejects missing or forged attestation data, re-verifies late/tool provenance, requires complete traced input for attested mode and rejects attempts to downgrade it into observational Shadow mode.
3. **Adapter mapping**: Python framework normalization propagates content attestation and source version alongside source/resource IDs.
4. **Real HTTP synthetic source custody test**: `customer_simulation/trusted_source_ingester.py` provides a local HTTP source simulation whose signing key is not supplied to the customer RAG. The integration test fetches signed content from that service, passes it through the actual Guard HTTP interface, authorizes legitimate content, and blocks simulated byte substitution under a valid resource ID.
5. **SSE transport correctness**: `drive-rag-demo/app.py` emits real standards-conformant SSE newlines, waits for both enforcement layers before transmission, and JSON-escapes generated event payloads.
6. **Customer-visible local route observation**: `customer_simulation/route_probe.py` checks JSON and SSE endpoints using allowed, denied and invalid synthetic identity tokens and asserts output bytes against registered synthetic canaries. It rejects remote destinations, malformed route URLs and HTTP redirects. This is deliberately **not** a customer protection certificate or active-mode switch.
7. **Explicit post-generation failure test**: an HTTP fault-injected Guard can permit Layer 1 but block Layer 2 after simulated model generation. The observed customer SSE response contains none of the protected generated bytes.
8. **Repeatable validation**: `customer_simulation/run_full_enterprise_validation.py` now explicitly runs the new source attestation/SSE/route observer subset and reports a real machine-readable outcome.

## Second continuation: actual strict-mode customer HTTP integration

The Google Drive RAG demo's protected JSON/SSE routes now support an **explicit opt-in** `ACCESSPROOF_DEMO_REQUIRE_ATTESTED_CONTENT=1` configuration with:
- `ACCESSPROOF_DEMO_ATTESTATION_TENANT`
- `ACCESSPROOF_DEMO_ATTESTATION_KEY_ID`
- `ACCESSPROOF_DEMO_ATTESTATION_PUBLIC_KEY_B64`

The demo receives only a trusted Ed25519 public key. It never creates signing keys or signs retrieved text. If strict mode is selected with missing or invalid public key configuration, the endpoint returns HTTP 503 rather than silently accepting metadata-only provenance. Unattested documents are blocked by the SDK.

The actual local customer HTTP integration was exercised with a separate synthetic source-ingestion HTTP server. It fetched two independently signed synthetic documents, allowed only the Guard-authorized one to reach the real customer SSE endpoint, and blocked a subsequent substitution of payroll bytes beneath its previously valid document ID/signature. The response emitted none of the substituted content.

**Strict-mode customer-route integration is therefore demonstrated only with synthetic signed source ingestion.** The ordinary Google Drive demo's real provider refresh path does not yet obtain source-backed attestations and therefore cannot complete this strict mode. That is an explicit remaining blocker to production certification, not a reason to downgrade verification.

The independent local route-probe component checks six scenarios (authorized, denied and invalid identities across JSON and SSE), plus negative cases for output leaks, invalid SSE and SSRF-like destinations.

The intended production integration must place the private signing key in a separate authenticated provider ingestion worker, securely fetch source content and versions, ensure all indexed chunks carry the correct signed origin, pin the verification key at the customer Guard/SDK boundary, include all generation inputs and tools in a trusted manifest, and prove the exact response-delivery route is intercepted. The local test intentionally does NOT switch on the product's `CUSTOMER_RAG_CHALLENGE_AGENT_REQUIRED` activation gate.

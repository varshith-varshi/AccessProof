# Protect activation and evidence state

**Customer action**: `Enable Protection` → organization-admin authenticated API `POST /protection/enable` → idempotent, tenant-bound `ProtectionActivationRun` and automatic stored readiness checklist. Status route returns `action_required`, exact unmet reason and last check. Retry re-runs current checks. No manual IDs or customer-supplied PASS booleans. Local desktop/mobile browser and API auth/tenant tests passed.

**Safety**: A run's state is not 'active' and `guard_acknowledged=false` absent a customer-side challenge verifier. Existing manual audit IDs can still be recorded by legacy API for compatibility, but Protect mode PATCH additionally gates on new real-RAG challenge requirement. The legacy Protect heartbeat-ACK protocol is independently regression-tested using explicit synthetic fixture override; it cannot substitute for customer route proof.

**Source-aware Microsoft gate:** `_application_checks` and policy distribution `source_acl_healthy` now verify the same per-source HMAC-signed provider-live certificate with an exact scope fingerprint. Lack of issuer, missing signing key, wrong tenant/drive/root/profile, stale source, tampering or expiry all deny. This replaces an unconditional provider-string false in the source-health/readiness logic without awarding any real certificate by default. Google remains subject to existing source/Guard/identity freshness checks, plus missing customer-RAG automated challenge.

**Required to finish:** durable outbound machine-authenticated challenge queue/leases and nonce, Guard+RAG trusted route manifest, signed machine test evidence, real positive/negative/provenance and zero output-byte cases, exact audit join, certificate issuer bound to observed real-provider results, atomic pending state and authenticated Guard install ACK, periodic health/re-certification and revocation. Current implementation is a **secure activation preflight**, not completed one-click activation.
